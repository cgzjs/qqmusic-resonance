# 同频 v0.7 · 第二步：真实双人交换

日期：2026-09-20。范围为既有共听会话内的双向推荐与账号记录，使用四段内置试听，不接入正式 QQ 曲库或真实位置。

## 用户体验

- 在线同频成功后，双方均可点击“交换一首”，选歌送出；每个会话同时只有一份待回应交换。
- 接收方收到页内提示，可选另一首回应、婉拒或忽略。发起方等待时可撤回。
- 60 秒服务端时限；断线不重置倒计时，重连恢复同一份状态；过期后旧回应不能完成交换。
- 完成后两端各自看到自己送出和收到的歌，可收藏、加入待听或收起；不会自动收藏、自动播放或切换公共曲目。
- 足迹中新增“在线交换”，展示送出与收到关系，收到的歌可在足迹重播；场景演示交换保留原标识。
- 待回应时会话结束则交换终止，完成的结果继续保留。切号与授权失效沿用现有会话退出规则。

## 状态与权限

| 状态 | 发起方 | 接收方 |
| --- | --- | --- |
| 选歌 | 选择一首并发送 | — |
| 待回应 | 撤回、等待 | 选不同歌曲回应、婉拒、忽略 |
| 已完成 | 保存收到的歌、再交换 | 保存收到的歌、再交换 |
| 婉拒/撤回/到期 | 查看结果、再次发起 | 查看结果、再次发起 |
| 会话结束 | 查看已完成结果、回足迹 | 查看已完成结果、回足迹 |

双方均在线才可发起和回应；撤回/婉拒允许自己仍在线时执行。服务端验证双方账号授权，角色来自已认证连接，不接受客户端自报身份。只允许固定曲库，回应不能和收到的歌相同。

每条指令有稳定 UUID 和时间；客户端等待 8 秒仍未确认时保留该指令，用户可显式“重试确认上次操作”，不自动重发。服务端已处理的同 ID 指令返回当前状态；未处理且超过 10 秒的旧指令拒绝，需重新操作。播放状态与交换语义分开，不以交换动作改变音轨。

## 可靠保存

- 成功回应后，交换结果和双方账号投递任务先写入会话 Durable Object，再向两端确认完成。
- 随后分别写入双方账号。页面区分“交换已确认”“我的足迹已保存”“双方足迹已保存”，不会把单端成功说成双方成功。
- 账号用 roomId + exchangeId 去重，记录及去重标记在同一个存储事务中写入；最近 100 条在线交换用于展示，去重标记保留，避免旧投递在历史裁剪后重复入库。
- 一端失败时只重试未成功的一端，采用递增重试间隔、最大 60 秒。关闭会话后保留未完成投递及 alarm，直到保存成功；服务重启后继续恢复。
- 每个会话最多 100 次发起、最多 10 份未完成投递，防止原型无限积压；超限不影响既有播放和退出。
- 写入账号的内部端点仅由 Worker 绑定调用，公共 `/api/host` 不开放该端点；客户端不能伪造在线交换历史。

## 界面复用

复用现有专辑块、选歌行、音乐卡片/星光素材、青色按钮和减少动态效果规则。交换面板可收起，收到新交换时自动呈现该份内容；页面上方提供查看待回应交换入口。重开一份交换时清理上一份保存提示，不把旧提示套在新歌上。

## 验证与剩余边界

- 状态机与协议测试：角色、并发、曲库、不同回应、婉拒/撤回、边界超时、失效指令和数据校验。
- 本地真实服务：双向竞争仅一份成功；重复回应不重复保存；断线恢复待回应状态；实际等待 60 秒超时；完成后立即结束会话仍保留双方记录。
- 浏览器双账号已验证选歌、回应、双方结果、分别收藏/待听、退出后足迹及重播，公共播放曲目和暂停状态保持不变；375px 完成页已目视检查。
- 生产构建故障注入测试单独使用测试 Worker 代理：让一个账号写入失败，关闭会话并重启 Worker，再恢复写入，检查双方各留一条正确记录。应用本身不新增故障开关或测试后门。
- 最终 35 项测试通过（原 28 项回归 + 4 项交换协议/重试测试 + 2 项真实服务测试 + 1 项生产构建故障恢复测试）。故障注入实测部分保存、会话关闭和 Worker 重启后仍能补齐双方记录且不重复。类型检查、lint 与构建通过。
- 公网、跨设备、真实 QQ SDK 与正式曲库仍未接入；没有新增聊天或好友关系。

测试：`npm run test:exchanges`；本地服务运行时 `npm run test:exchanges:integration`；先构建后执行 `npm run test:exchanges:durability`。故障注入测试的临时存储留在系统临时目录，便于失败时排查。
