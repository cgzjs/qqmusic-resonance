# v1.1 刷新后恢复等待

发送后的等待由当前账号服务保存，适用于场景交换、挥手和喜欢。真实双人互动继续由双方客户端操作，不加入自动回应。

## 行为

- 服务端接受请求时保存固定请求编号、原歌曲与回应、约 2.6 秒后的截止时间。刷新、切换页面或重新登录不重新开始计时。
- 到期由账号 Durable Object alarm 处理；重新读取账号时也检查到期任务，页面未打开时仍能完成已确认的交换。
- 交换完成与写入足迹在同一账号保存中完成，沿用交换 ID，产生一条未读回歌。
- 客户端恢复后先读取已有状态：未到期显示等待，已到期显示回应；不自动播放、不强制跳到结果页。
- 通知由服务端原子认领。同账号多个页面只有一个页面取得弹窗，已经展示过的回应不因刷新而重弹；关闭提示不等于将回歌标为已读。
- 切号后原账号的请求保留在原账号，界面与迟到回调不会混入当前账号。
- 每个账号最多同时等待一份交换和一份轻回应。重复请求不延后时间、不重复记录；相同编号但不同内容会拒绝。
- 网络失败时显示未确认，重试沿用原请求编号；服务器尚未接受的请求不承诺恢复。
- 通知认领后若页面恰好关闭或响应丢失，不再重复认领；交换记录仍在“收到的歌”中。这是弹窗去重的边界，不影响回歌持久化。

## 验证

- `npm run test:replies:integration` 验证原截止时间、重新授权恢复、重复提交、并发通知认领、跨账号拒绝，以及无客户端轮询时完成交换和回应。
- 客户端测试验证组件重新挂载后读取待回应状态、已认领不重复弹窗、账号卸载后忽略迟到结果；原回歌未读测试继续通过。
- 浏览器验证送歌后立即刷新仍收到回歌，再次刷新不重弹；点赞后刷新仍收到原歌曲回应。
- 后续“今日交换”统计已统一，规则见产品主文档。真机联调继续暂缓。
